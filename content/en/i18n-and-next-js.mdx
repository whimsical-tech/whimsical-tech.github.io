Now, let's create a few fundamental files.
First, we need the basic configuration of our project.

I'm calling this file ```i18n-config.ts```. Let's put it in the root folder.

```ts

  defaultLocale: "ja",
  locales: ["en", "ja"],
} as const;

export type Locale = (typeof i18n)["locales"][number];

export const hasLocale = (locale: string): locale is Locale =>
  locale in i18n.locales;
```

Now your app is only accessible if you manually type /en or /ja in the url.
Let's create a proxy.ts file in the same level as your app folder.
Please notice, if you are using an older version of Next.js (below 16), you will need a middleware file instead.

```ts
import { NextRequest, NextResponse } from "next/server";
import { i18n, Locale } from "./i18-config";

const { defaultLocale, locales } = i18n;

function getLocale(request: NextRequest) {
  const acceptLanguage = request.headers.get("accept-language");
  if (!acceptLanguage) return defaultLocale;

  const preferredLocales = acceptLanguage.split(",").map((lang) => {
    const code = lang.split(";")[0].replace(/\s+/g, "");
    return code.substring(0, 2);
  });

  const matched = preferredLocales.find((lang) =>
    locales.includes(lang as Locale),
  );
  return matched ?? defaultLocale;
}

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const pathnameHasLocale = locales.some(
    (locale) => pathname.startsWith(`/${locale}/`) || pathname === `/${locale}`,
  );

  if (pathnameHasLocale) return;

  const locale = getLocale(request);
  request.nextUrl.pathname = `/${locale}${pathname}`;

  const response = NextResponse.redirect(request.nextUrl);
  return response;
}

export const config = {  matcher: [
    "/((?!_next|public|favicon\\.ico|.*\\.(?:png|jpg|jpeg|gif|webp|svg|ico)$).*)",
  ],
};
```

If your app can't automatically detect the proxy, add it explicitly to tsconfig.json:

```
"include": [
  "proxy.ts"
]
```

Next, we want to offer our users an in-built way to change languages.
Most people will not simply try to change the URL!
So let's create a locale switcher.
Since I promised to help even if you want to add multiple languages, a dropdown with options is a scalable choice.

```tsx
"use client";

import { useRouter, usePathname } from "next/navigation";
import { useTransition } from "react";
import { Locale } from "@/i18n-config";

const locales: Record<Locale, { name: string; flag: string }> = {
  en: { name: "English", flag: "🇬🇧" },
  ja: { name: "日本語", flag: "🇯🇵" },
};

export default function LanguageSwitcher() {
  const router = useRouter();
  const pathname = usePathname();
  const [isPending, startTransition] = useTransition();

  const currentLocale: Locale = pathname.startsWith("/ja") ? "ja" : "en";

  const handleChange = (event: React.ChangeEvent<HTMLSelectElement>) => {
    const newLocale = event.target.value as Locale;

    startTransition(() => {
      const segments = pathname.split("/").filter(Boolean);

      if (currentLocale === newLocale) return;
      if (segments[0] === currentLocale) segments[0] = newLocale;

      const newPath = `${segments.join("/")}`;

      router.replace(newPath);
    });
  };

  return (
    <div
      style={{ display: "inline-flex", alignItems: "center", gap: "0.5rem" }}
    >
      <select
        id="language-select"
        value={currentLocale}
        onChange={handleChange}
        disabled={isPending}
      >
        {Object.entries(locales).map(([code, { name, flag }]) => (
          <option key={code} value={code}>
            {flag} {name}
          </option>
        ))}
      </select>
      {isPending && <span>Switching...</span>}
    </div>
  );
}
```

Now, let me show you how to add the translations in client components.
Remember this is not the ideal solution as they might slug behind the server components and cause hydration issues.

If you are already familiar with React Context, you'll know it's a way to easily provide information across your app without having to endless pass props along the tree.
In similar fashion, we will use a Provider in layout.tsx to pass the language along the entire app.

```tsx
"use client";

import { ReactNode, useEffect } from "react";
import { I18nextProvider, initReactI18next } from "react-i18next";
import i18next from "i18next";
import en from "../../locales/en.json";
import ja from "../../locales/ja.json";

if (!i18next.isInitialized) {
  i18next.use(initReactI18next).init({
    resources: {
      en: { locale: en },
      ja: { locale: ja },
    },
    fallbackLng: "en",
    ns: ["locale"],
    defaultNS: "locale",
    interpolation: {
      escapeValue: false,
    },
  });
}

export function I18nProvider({
  children,
  lang,
}: {
  children: ReactNode;
  lang: string;
}) {
  useEffect(() => {
    if (!i18next.isInitialized || i18next.language !== lang) {
      i18next.changeLanguage(lang);
    }
  }, [lang]);

  return <I18nextProvider i18n={i18next}>{children}</I18nextProvider>;
}

```

layout.tsx
```tsx
    <html lang={lang} className={notoSansJp.variable}>
      <body>
        <!-- add the provider to the main layout.tsx of your project -->
        <I18nProvider lang={lang}>{children}</I18nProvider>
      </body>
    </html>
```

For this next example let's continue in ```LastVisitNotice.tsx``` and take a look at the remaining untranslated string.
It is much more complex than the strings we've translated so far. It contains two props and three ```<strong>``` tags.

There is more than one way to handle this. One possibility is to use template strings.
```tsx
{t("lastVisit.mainText", {
  date: formatVisitDate(locale),
  count: NEW_LISTING_COUNT,
})}
```

```json
"lastVisit.mainText": "前回のご訪問は {{date}} でした。その後、新着物件が {{count}} 件 加わっています。一覧では NEW の付いた物件を先頭に並べています。"
```

(the below should be in its own box if possible)
P.S.: You will also notice I changed ```function formatVisitDate()``` to accept a locale parameter.
I also moved the function inside the component so we can access the ```t()``` and added a correspondent string to "不明な日時" in the json files.
```ts
function formatVisitDate(locale: string) {
  const d = new Date();
  if (Number.isNaN(d.getTime())) return t("unknownDate");
  return new Intl.DateTimeFormat(locale, {
    year: "numeric",
    month: "long",
    day: "numeric",
    weekday: "short",
  }).format(d);
}
```

Template strings work great if all you want is to add some props to your translation, but you might have noticed I removed the ```<strong>``` tags from this solution.
That's because normally React would not be able to read tags from the text, and we would have to add something like ```dangerouslySetInnerHTML```, which I prefer to avoid.

If there is a need for html in the strings, we can use a handy component from ```react-i18next``` library called ```Trans```.
```tsx
<Trans
  i18nKey="lastVisit.mainText"
  values={{
    date: formatVisitDate(locale),
    count: NEW_LISTING_COUNT,
  }}
>
  <strong>date</strong>
  <strong>count</strong>
  <strong>NEW</strong>
</Trans>
```

Use the html you want inside ```<Trans>```. The text is just a placeholder, and it is not relevant.
This is how to implement it in the json side, notice the increasing numbers wrapped in tags. They will directly correlate to the elements you are using in the tsx.

ja.json
```json
 "mainText": "前回のご訪問は <1>{{date}}</1> でした。その後、新着物件が <3>{{count}} 件</3> 加わっています。一覧では <5>NEW</5> の付いた物件を先頭に並べていま。"
```

en.json
```json
 "mainText": "Your last visit was <1>{{date}}</1>. Since then, <3>{{count}} new listings</3> have been added. In the list, listings with <5>NEW</5> are displayed at the top."
```

You might be thinking, can't I just use multiple strings instead?
Perhaps you could have used a string for "Your last visit was  ", then show the prop as usual in the tsx, then continue with another string ". Since then, ", then the next prop, and so on.
Then there is no need for template strings or external components.
However, not only is that more complicated and more difficult to read, it can also easily introduce errors as different languages have different flows and word order.
Even in the example above, you don't need to know both English and Japanese to realize the first full stop comes in English right after the prop, where as in Japanese there is one more word.
And in other languages the structure could vary even more widely, and perhaps the prop should even start the sentence.
To make sure to account for all differences and understand them at a glance, make sure to use Trans or a template string when there are props involved!

Naming things
As I was focused on explaining different scenarios, my current locale files only have 4 keys.
```
{
  "lastVisit": {
    "dateWarning": "※表示される日付はいつも今日の日付です（デモ用のローカル表示）",
    "mainText": "前回のご訪問は <1>{{date}}</1> でした。その後、新着物件が <3>{{count}} 件</3> 加わっています。一覧では <5>NEW</5> の付いた物件を先頭に並べていま。"
  },
  "slogan": "日本各地の売買・賃貸をワンストップでサポートします",
  "unknownDate": "不明な日時"
}```

There is no right or wrong way to set up the locale files, it varies depending on the needs of your application.
Of course, you want to make sure all keys are unique and easy to identify. "mainText", for example, should not be a key by itself. mainText of what?

It is a good idea to keep all or most translations nested, like in lastVisit.
You can see a more extended example of this in the final version of the project, where I translated all strings.

But you don't need to have only 1 file per language.
Especially if your project is large, you may want folders for each language, and instead of nesting translations in a object, you may want each locale file to correspond to a page or component in your application.
Something like:

- locales
  - en/
    - lastVisitNotice.json
    - propertyDetail.json
    - aboutPage.json
    - ...
  - jp/
    - lastVisitNotice.json
    - propertyDetail.json
    - aboutPage.json
    - ...

Bonus: Currency
Currency is a complicated topic that deserves its own article.

In a real world scenario, you will want to track currency and language separately.
For example, maybe in your project a Japanese person who lives abroad is trying to buy something from your website.
They might pay in Euro, but it is likely they would prefer the UI in their native language.
The same language can also represent different currencies. Both U.S. and U.K. speak English, but one uses dollars and the other uses pounds.

But the truly delicate matter is the conversion. Conversion changes all the time, and making that kind of calculation in the frontend is generally unwise.
In most cases you'll want the backend to send you the correct raw number and in the tsx just handle the transformation.

You can then use ```Intl.NumberFormat``` or a library such as currency.js or money.js.
