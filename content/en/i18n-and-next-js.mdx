## Basic settings

As you might have expected, the first thing we have to do is installing some packages.

`npm install i18next react-i18next`

Then, let's create a few fundamental files.
First, we need the basic configuration of our project.

I'm calling this file ```i18n-config.ts```. Let's put it in the root folder.

```ts
export const i18n = {
  defaultLocale: "ja",
  locales: ["en", "ja"],
} as const;

export type Locale = (typeof i18n)["locales"][number];

export const hasLocale = (locale: Locale) => {
  return i18n.locales.includes(locale);
}
```

This is the file where you define which language should be the default in your website, include the array with the languages you'll be using, and a simple check that matches languages against the one present in your app to see if there is a match.

The next thing we want is to load our translations. It needs to be a separate file because import() can cause bundling issues during Node.js buildtime.

Next file: locales.ts

```ts
import type { Locale } from "./i18n-config";

const locales = {
  en: () => import("../locales/en.json").then((module) => module.default),
  ja: () => import("../locales/ja.json").then((module) => module.default),
};

export const getTranslation = async (locale: Locale) =>
  locales[locale]?.() ?? locales.ja();

```

Make sure to also create a folder with files that matches the loaded path.
In case you're using the file above verbatim, that means you'll create a folder ```locales``` with files ```en.json``` and ```ja.json```.
If you're using other languages, make sure to add them accordingly.
To avoid compilation errors, make sure to add empty curly braces {} in all of the translation files. 

```en.json```, ```ja.json```, any translation file:
```
{}
```

Later we will add all translated strings there, but for now let's continue our configuration.
Directly under the app folder, create a folder called [lang].
The brackets are important, they specify lang is a dynamic parameter.
Inside [lang] you should have all of your pages.

![This is how the directory currently looks like](../../directory.png "This is how the directory currently looks like")

Right now your app is only accessible if you manually add a parameter in the url.
To fix this, let's create a proxy.ts file in the same level as your app folder.
Please notice, if you are using an older version of Next.js (below 16), you will need a middleware file instead.

```ts
import { NextRequest, NextResponse } from "next/server";
import { i18n, Locale } from "./i18n-config";

const { defaultLocale, locales } = i18n;

function getLocale(request: NextRequest) {
  const acceptLanguage = request.headers.get("accept-language");
  if (!acceptLanguage) return defaultLocale;

  const preferredLocales = acceptLanguage.split(",").map((lang) => {
    const code = lang.split(";")[0].replace(/\s+/g, "");
    return code.substring(0, 2);
  });

  const matched = preferredLocales.find((lang) =>
    locales.includes(lang as Locale),
  );
  return matched ?? defaultLocale;
}

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const pathnameHasLocale = locales.some(
    (locale) => pathname.startsWith(`/${locale}/`) || pathname === `/${locale}`,
  );

  if (pathnameHasLocale) return;

  const locale = getLocale(request);
  request.nextUrl.pathname = `/${locale}${pathname}`;

  const response = NextResponse.redirect(request.nextUrl);
  return response;
}

export const config = {  matcher: [
    "/((?!_next|public|favicon\\.ico|.*\\.(?:png|jpg|jpeg|gif|webp|svg|ico)$).*)",
  ],
};
```

After this implementation, even if there are no language params in the url, an automatic redirection will occur.
However, because we haven't changed the contents yet, we are seeing the same strings for all languages.

Let's handle that next!

Go to the layout.tsx file encompassing the whole application.
There is a lang attribute in the HTML, and you no longer want this value to be static.

From now we will read locale from the url params like this:

```tsx
export default async function RootLayout({ 
  children,
  params, 
}: Readonly<{
  children: React.ReactNode;
  params: Promise<{ lang: Locale }>;
}>) {
  const { lang } = await params;
  return (
    <html lang={lang} ...
```

The important things to notice is to make the function async, to add params to props and to get lang from awaited params.

You can check if it's working by inspecting the live code in the browser and checking if the ```<html lang="">``` is changing as you change language in the url.
Only languages specified in your config file will be valid.

Also add to the same file:
```tsx
export async function generateStaticParams() {
  return [{ lang: "en" }, { lang: "ja" }];
}
```

We are getting there!

Next, we want to offer our users an in-built way to change languages, so let's create a locale switcher.
Since I promised to help even if you want to add multiple languages, a dropdown with options is a scalable choice.
I added it to components folder.

```tsx
"use client";

import { useRouter, usePathname } from "next/navigation";
import { useTransition } from "react";
import { Locale } from "@/i18n-config";
import { useTranslation } from "react-i18next";

const locales: Record<Locale, { name: string; flag: string }> = {
  en: { name: "English", flag: "🇬🇧" },
  ja: { name: "日本語", flag: "🇯🇵" },
};

export default function LanguageSwitcher() {
  const router = useRouter();
  const pathname = usePathname();
  const { i18n } = useTranslation();
  const [isPending, startTransition] = useTransition();

  const currentLocale = i18n.language;

  const handleChange = (event: React.ChangeEvent<HTMLSelectElement>) => {
    const newLocale = event.target.value as Locale;

    startTransition(async () => {
      await i18n.changeLanguage(newLocale);

      const newPath = pathname.replace(`/${currentLocale}`, `/${newLocale}`);
      router.push(newPath);
    });
  };

  return (
    <div
      style={{ display: "inline-flex", alignItems: "center", gap: "0.5rem" }}
    >
      <select
        id="language-select"
        value={currentLocale}
        onChange={handleChange}
        disabled={isPending}
      >
        {Object.entries(locales).map(([code, { name, flag }]) => (
          <option key={code} value={code}>
            {flag} {name}
          </option>
        ))}
      </select>
      <span
        style={{
          display: "inline-block",
          width: "16px",
          height: "16px",
          visibility: isPending ? "visible" : "hidden",
        }}
        aria-hidden={!isPending}
      >
        {isPending && <div className="spinner" />}
      </span>
    </div>
  );
}
```

## From hardcoded strings to text fetched from translation files
When using translations in Next.js, you can load them client-side or server-side.
Server-side is generally preferable since it is instantaneous, so let's talk first about this method.

I will use SiteHeader.tsx as starting point, you can pick any clearly visible string from your own project.

In line 14 you will see this hardcoded string: "日本各地の売買・賃貸をワンストップでサポートします"
In English this might be roughly translated as: "One-stop support for buying, selling, and renting throughout Japan"

All translated strings in your project will be represented by a JSON value. For this example, slogan would be a good name.
So in en.json, please write:

```
{slogan: "One-stop support for buying, selling, and renting throughout Japan"}
```

In ja.json, please write: 

```
{slogan: "日本各地の売買・賃貸をワンストップでサポートします"}
```

And in the tsx, replace the hardcoded string with  ```{t["slogan"]}```
You can name "t" anything you want. Maybe you prefer to use the full word "translate".
Now let's make the changes to whichever component you are adding the translations to.
Remember, it must be a Server component!

Since we need to extract the locale from params, first we want to retrieve it on the parent page.
```tsx
export default function Home({
  params,
}: {
  params: Promise<{ lang: Locale }>;
}) {
  const { lang } = await params;
  const t = await getTranslation(lang);

  return (
    <div className={styles.page}>
      <SiteHeader active="home" lang={lang} t={t}  />
      ...
```

Then we pass it to the component where the translations are used, in our case ```SiteHeader.tsx```.

```tsx
export async function SiteHeader({
  active,
  lang,
  t,
}: {
  active: NavKey;
  lang: Locale;
  t: Awaited<ReturnType<typeof getTranslation>>;
}
```

In most cases, you will not need to pass both the locale and the getTranslation props, only the latter should suffice.
However, since SiteHeader.tsx contains navigation links, we need to add lang to construct localized URLs, so remember to apply this pattern to any component containing links that need to respect the current locale.

```tsx
  <Link href={`/${lang}/`} className={styles.brand}>
    ...
  </Link>
  <nav className={styles.nav} aria-label="主要ナビゲーション">
    <Link
      href={`/${lang}/`} >
      ...
    </Link>
    <Link
      href={`/${lang}/about`} 
      ...
```
You should now see the localized strings and maintain correct locale while navigating.
The oversimplified version is: do this for all server components and we are done!

### Client side
For interactive client components where server rendering is not possible, we need to use a different pattern.

If you are already familiar with React Context, you'll know it's a way to easily provide information across your app without having to endless pass props along the tree.
In similar fashion, we will use a Provider in layout.tsx to pass the language along the entire app.

```tsx
"use client";

import { ReactNode, useEffect } from "react";
import { I18nextProvider, initReactI18next } from "react-i18next";
import { Locale } from "@/i18n-config";
import i18next from "i18next";
import en from "../../locales/en.json";
import ja from "../../locales/ja.json";

export function I18nProvider({
  children,
  lang,
}: {
  children: ReactNode;
  lang: Locale;
}) {
  useEffect(() => {
    if (!i18next.isInitialized || i18next.language !== lang) {
      i18next.changeLanguage(lang);
    }
  }, [lang]);

  return <I18nextProvider i18n={i18next}>{children}</I18nextProvider>;
}

```

Then, add the provider to the main layout.tsx of your project.

```tsx
  const { lang } = await params;
  const currentLang = lang as Locale;
  return (
    <html lang={lang} className={notoSansJp.variable}>
      <body> 
        <I18nProvider lang={currentLang}>{children}</I18nProvider>
      </body>
    </html>
  );
```

```LastVisitNotice.tsx``` is a client component, so it is the perfect use case to test our provider.
I'm replacing our hardcoded string ```※表示される日付はいつも今日の日付です（デモ用のローカル表示）``` with ```{t("lastVisit.dateWarning")}``` and then adding ```lastVisit.dateWarning``` to the json files.

```

    "dateWarning": "The displayed date is always today's date (local display for demo purposes)"

```


### Client-side loading considerations
A Flash of Untranslated Content (FOUC) can occur when translations are loaded on the client-side.
This is bad UX.

Let's recap:
- Server Components can get the correct dictionary by getting the params from the page
- Client Components can share a Provider 
- Ensure a loading state for client components to avoid FOUC 
- Remember to update all internal links to include locale
- Include all translated strings in the corresponding json files, and replace in the tsx accordingly

### Adding props and html to translations
For this next example let's continue in ```LastVisitNotice.tsx``` and take a look at the remaining untranslated string.
It is much more complex than the strings we've translated so far. It contains two props and three ```<strong>``` tags.

There is more than one way to handle this. One possibility is to use template strings.
```tsx
{t("lastVisit.mainText", {
  date: formatVisitDate(locale),
  count: NEW_LISTING_COUNT,
})}
```

```json
"lastVisit.mainText": "前回のご訪問は {{date}} でした。その後、新着物件が {{count}} 件 加わっています。一覧では NEW の付いた物件を先頭に並べています。"
```

**_Displaying date in local format_**

You will also notice I changed ```function formatVisitDate()``` to accept a locale parameter.
I also moved the function inside the component so we can access the ```t()``` and added a correspondent string to "不明な日時" in the json files.
```ts
function formatVisitDate(locale: string) {
  const d = new Date();
  if (Number.isNaN(d.getTime())) return t("unknownDate");
  return new Intl.DateTimeFormat(locale, {
    year: "numeric",
    month: "long",
    day: "numeric",
    weekday: "short",
  }).format(d);
}
```

We can get the locale through context:
```tsx
const { t, i18n } = useTranslation();
const locale = i18n.language;
```

The import is also updated to:
```tsx
import { Trans, useTranslation } from "react-i18next";
```

Template strings work great if all you want is to add some props to your translation, but you might have noticed I removed the ```<strong>``` tags from this solution.
That's because normally React would not be able to read tags from the text, and we would have to add something like ```dangerouslySetInnerHTML```, which I prefer to avoid.

If there is a need for html in the strings, we can use a handy component from ```react-i18next``` library called ```Trans```.
**Trans can only be used in client components.**
Go ahead and replace the paragraph with the code below:

```tsx
<Trans
  i18nKey="lastVisit.mainText"
  values={{
    date: formatVisitDate(locale),
    count: NEW_LISTING_COUNT,
  }}
/>
```

Now we can use the HTML tags directly in the translation files!

ja.json
```json
 "mainText": "前回のご訪問は <strong>{{date}}</strong> でした。その後、新着物件が <strong>{{count}} 件</strong> 加わっています。一覧では <strong>NEW</strong> の付いた物件を先頭に並べていま。"
```

en.json
```json
 "mainText": "Your last visit was <strong>{{date}}</strong>. Since then, <strong>{{count}} new listings</strong> have been added. In the list, listings with <strong>NEW</strong> are displayed at the top."
```

### Splitting translation strings
You might be thinking: "Instead of using ```<Trans>``` or template strings, can I not use multiple strings?"
Perhaps a string for ___"Your last visit was  "___, then show the prop as usual in the tsx, then continue with ___". Since then, "___, then the next prop, and so on.
By doing that, there is no need for template strings or external components.

If you want to avoid ```dangerouslySetInnerHTML```, this is indeed the pattern for server-side translations, since ```<Trans>``` is not available.
However, for client side there is no need to split translations like that. Not only that's more difficult to read, it can also easily introduce errors as different languages have different flows and word order.
In the example above, the first full stop comes in English right after the value, whereas in Japanese there is one more word. In other languages the structure could vary even further, and perhaps the value would start the sentence.
To account for all differences and understand them at a glance, make sure to use ```<Trans>``` or a template string when dealing with client components.

## Naming things
If so far you have strictly followed the tutorial without adding extra translations, your current locale files only hold 4 keys.
```json
{
  "lastVisit": {
    "dateWarning": "※表示される日付はいつも今日の日付です（デモ用のローカル表示）",
    "mainText": "前回のご訪問は <1>{{date}}</1> でした。その後、新着物件が <3>{{count}} 件</3> 加わっています。一覧では <5>NEW</5> の付いた物件を先頭に並べていま。"
  },
  "slogan": "日本各地の売買・賃貸をワンストップでサポートします",
  "unknownDate": "不明な日時"
}
```

It's simple now, but as we add more and more strings, it can get quite chaotic.

There is no single correct way to set up the locale files, it varies depending on the needs of your application.
The most important rule is uniqueness and context, for example, avoid generic keys like "mainText" in isolation. It'd make one wonder: main text of what?
By nesting it in lastVisit, it becomes clear and self-documenting.

I also recommend keeping the strings in alphabetical order. I used the website [https://novicelab.org/jsonabc/](https://novicelab.org/jsonabc/) to easily reorder the files in English character order (A-Z).

You can see a more extended example of this in the final version of the project (master branch), where all strings are translated.

So far in the tutorial we have loaded all keys from either en.json or ja.json, but large applications often benefit from multiple files per locale.
You may want folders for each language, and each locale file may correspond to a page or component in your application.
Something like:

- locales
  - en/
    - aboutPage.json
    - lastVisitNotice.json
    - propertyDetail.json
    - ...
  - jp/
    - aboutPage.json
    - lastVisitNotice.json
    - propertyDetail.json
    - ...

To implement that, include the new files in the i18n initialization, which we are doing in the I18nProvider, and the settings in ```locales.ts```.
You'll also need to change getTranslation to look for the locale in the folder and accept a second parameter to load the intended file.

## Bonus: Currency

Currency is a complicated topic that deserves its own article.

In a real world scenario, you will want to track currency and language separately.
For example, maybe in your project a Japanese person who lives abroad is trying to buy something from your website.
They might pay in Euro, but it is likely they would prefer the UI in their native language.
The same language can also represent different currencies. Both U.S. and U.K. speak English, but one uses dollars and the other uses pounds.

The truly delicate matter is the conversion. Conversion changes all the time, and making that kind of calculation in the frontend is generally unwise.
In most cases you'll want the backend to send you the correct raw number and in the tsx just handle the transformation.

You can then use ```Intl.NumberFormat``` or a library such as currency.js or money.js.
